第一章：UART 给你的只是连续字节

USART 硬件只保证字节按顺序到达。它不知道什么叫“一个业务数据包”，也不会自动处理以下情况。

半包

第一次到达：AA 55 02 48 稍后才到：69 23

第一次检查时帧还不完整，已经收到的字节必须保留。

粘包

AA 55 02 48 69 23 AA 55 01 41 40

两帧连续到达，硬件不会在两帧中间插入分隔通知。

前置噪声

11 22 33 AA 55 02 48 69 23

解析器必须跳过无效字节，重新找到真正的包头。

错误包头或校验

解析失败后不能把整个缓冲区清空，因为错误字节后面可能紧跟着正常帧。

第一个设计结论：“收到一个字节”和“收到一个完整包”是两件事，必须放在不同层处理。

第二章：先分层，再开始写函数

1. USART ISR读取 DR，处理 ORE。越短越好
2. 环形队列保存尚未解析的原始字节。解耦中断与任务
3. ReadPacket找包头、读长度、等待半包、校验。一次最多返回一帧
4. PktTask处理纯 DATA，当前测试为原样回发。业务不进入 ISR

写代码前先确定四条不变量

  1. head 只由 ISR 修改，tail 只由接收任务修改。
  2. 没有确认错误或成功前，解析器不移动 tail。
  3. 错误时只丢一个字节，避免连带丢掉后面的正常帧。
  4. ISR 不等待发送、不打印、不解包。

这些不变量比某一行代码更重要。后面的辅助函数都围绕它们设计。

第三章：用环形队列积压原始字节

普通数组若不断删除队头，需要频繁搬移数据；环形队列只移动下标，适合持续接收。

ISR：单生产者

head 指向下一个可写位置，只由 RxPush() 推进。

任务：单消费者

tail 指向下一个未读位置，只由读取或解析函数推进。

空：head == tail。满：((head + 1) & MASK) == tail。

数组有256格，故意留一格区分空和满，所以最多同时积压255字节。

USART6_RX_BUF_SIZE = 256 USART6_RX_MASK = 255 (254 + 1) & 255 = 255 (255 + 1) & 255 = 0 /* 自动回到数组开头 */

为什么先写数组，再发布 head

buf[head] = data; /* 数据先真正写入数组 */ head = next; /* 再通知任务：有新字节可读 */

如果顺序反过来，任务可能先看到新的 head，随后读到尚未写好的数组内容。

解析器需要的三个辅助函数

函数作用是否移动 tail
RxCount()计算当前未读字节数否
RxPeek(offset)查看 tail 后第 offset 个字节否
RxDrop(n)确认后消费或丢弃 n 个字节是
核心思路：Peek 与 Drop 分开，相当于“先检查、后提交”。检查失败前不会破坏原始字节。

第四章：设计一种可以切分粘包的帧格式

AASOF0
55SOF1
LENDATA 长度
DATA0～64字节
XOR异或校验
字段为什么需要缺少它会怎样
SOF0 / SOF1从噪声中寻找候选起点出错后很难重新同步
LEN明确 DATA 的结束位置，直接切开粘包只能依赖超时或结束符猜边界
DATA交给业务层的有效载荷协议没有实际内容
XOR检查 LEN 和 DATA 是否出现常见错误可能把坏包交给业务层

载荷为 “Hi”

DATA = 48 69 LEN = 02 XOR = 02 ^ 48 ^ 69 = 23 整帧 = AA 55 02 48 69 23
  • LEN 不包含包头、LEN 自身和 XOR。
  • 最大完整帧长度：2 + 1 + 64 + 1 = 68 字节。
  • XOR 适合教学和轻量校验；正式协议可以换成 CRC16。

第五章：按“检查 → 等待 → 提交”写解析器

ReadPacket() 始终从当前 tail 开始。数据不足就返回0，成功就返回1；只有丢掉错误字节时才继续内部循环。

  1. 包头不足：保留队列，等待 ISR 继续接收。
  2. SOF 不匹配：丢1字节，重新查找包头。
  3. LEN 尚未到达：保留队列并返回。
  4. LEN 超过0～64：丢1字节，重新同步。
  5. 完整帧未到齐：保留半包，最多等待20ms。
  6. 半包超时或 XOR 错误：丢1字节，重新同步。
  7. 校验通过：复制 DATA、消费整帧、返回1。

先写伪代码，再翻译成 C

循环： n = 当前未读字节数 如果包头都不够：返回 0 如果 SOF0 错：丢 1 字节，继续 如果 SOF1 错：丢 1 字节，继续 如果 LEN 还没到：返回 0 如果 LEN 非法：丢 1 字节，继续 need = 包头 + LEN字段 + DATA + XOR 如果 n < need： 未超时：保留半包，返回 0 已超时：丢 1 字节，继续 如果 XOR 错：丢 1 字节，继续 复制 DATA 消费 need 个字节 返回 1

为什么错误时只丢一个字节

当前候选起点不成立，只能证明第一个字节不是正确起点，不能证明后面的整段都无效。滑动一个字节重新检查，是最保守的重新同步方式。

第六章：用真实字节流推演执行过程

正常帧：AA 55 02 48 69 23

检查读取位置结果
包头Peek(0)=AA，Peek(1)=55通过
长度Peek(2)=02dlen=2
整帧长度need=2+1+2+1需要6字节
校验02 ^ 48 ^ 69得到23，与帧尾相同
提交复制48 69，Drop(6)返回1

前置噪声：11 22 33 AA 55 02 48 69 23

tail 指向11不是 AA，Drop(1)。
tail 指向22仍不是 AA，再 Drop(1)。
tail 指向33仍不是 AA，再 Drop(1)。
tail 指向AA后面是55，按正常帧解析。

重复包头：AA 55 AA 55 02 48 69 23

第一次候选第三个字节被当成 LEN，即 0xAA=170，超过64。
只丢第一个AA队头变成 55 AA 55...。
55不是SOF0再丢一个字节。
重新对齐剩下 AA 55 02 48 69 23，正常解析。

粘包：两帧一次到达

AA 55 02 48 69 23 | AA 55 01 41 40 <------ 第一帧 ------> <---- 第二帧 --->

第一次调用只消费第一帧的6字节。第二帧仍在队列中；任务回发第一帧后立即进入下一轮，再取第二帧。

粘包不是错误：它只是队列里同时存在多帧。协议有 LEN，解析器逐帧消费即可。

第七章：把解析器放进 FreeRTOS 任务

执行位置负责什么禁止什么
USART6 ISR读 DR、处理 ORE、字节入队、立即返回等待 TXE、printf、解包、回发
USART6_PktTask调用 ReadPacket，成功后处理或回发 DATA同时调用 ReadByte 抢同一个 tail
main初始化、创建任务、启动调度器继续运行旧的逐字节回显
RXNE 中断读取一个字节，推入队列，马上返回。
PktTask 获得 CPU调用 ReadPacket()。
帧还不完整返回0，任务 vTaskDelay(1)，ISR 继续收字节。
帧完整且校验正确返回1，任务得到纯 DATA，再调用 SendPacket()。

第九章：常见错误、边界与练习

在 ISR 中解包或回发

等待 TXE/TC 会延长中断时间，影响其他中断和任务。

边检查边移动 tail

遇到假包头时无法恢复原始字节。应先 Peek，最后统一 Drop。

错误时清空整个队列

坏字节后面可能紧跟正常帧。只丢一个字节更容易重新同步。

ReadByte 与 ReadPacket 混用

两者都会修改同一个 tail，会把一帧拆散。

当前实现边界

  • 接收仍是逐字节 RXNE 中断，DMA + IDLE 尚未实现。
  • 队列满时丢新字节，当前没有溢出计数。
  • XOR 不是强校验，正式协议可改用 CRC16。
  • 发送仍轮询等待 TXE/TC，不能在 ISR 中调用。
